# SP12 recovery reconciliation — baseline `bb3fc379862271bcfdd8715564990f1073b7df83`

Read-only evidence reconciliation. No source, fixture, image, firmware variable, or workspace file was edited; no VM or build was run. The requested input SHA-256 values all match the supplied pins. Host filesystem free space was 101 GiB at review time, 21 GiB above the 80 GiB reserve; this report is the only owned output.

## Findings

**The retained physical record does prove the restored default SP12 system reached userspace, with a bounded claim.** `output/phase1/sp12-original-recovery-restore-apply-20261110.log` records successful `sp12-restore-recovery --apply`, the ESP remounted read-only, the three active ESP hashes equal to the recovery hashes, and the marker/no-staging postconditions. The subsequently named `sp12-fallback-post-recovery-boot-20261110.log` records host `cs-sp12`, running `7.3.0-sp12-v7.3-platform`, clean dpkg audit, `/boot/efi` from `/dev/sda1` vfat read-only, and active ESP hashes matching the same recovery manifest. Together with the snapshot note's explicit later-reboot confirmation, this supports a physical restored-default-kernel userspace boot. It does not prove a recovery-panel boot, a firmware rescue route, physical power-loss behavior, or that the separate corrected QEMU target clone reached userspace.

**The corrected QEMU recovery fixture remains short of userspace.** The first rescue run restored the ESP at `/dev/vdc` (`C1D2-E253`) but selected the distinct `/dev/vdd15` ESP (`C6A1-9AB9`) with BootNext; that loader reached GRUB, so that attempt did not test the restored ESP. The corrected run copied the exact restored `C1D2-E253` FAT bytes into a disposable GPT ESP, verified full-partition readback, and BootNext-selected that unique partition. Its EFI loader ran GRUB 2.14. GRUB's ESP stub sets `prefix=()/grub` but asks for `configfile /grub.cfg`; the selected target `/boot` filesystem contains `grub/grub.cfg`, not a root-level `grub.cfg`. Manually issuing `configfile ($root)/grub/grub.cfg` produced no captured menu/kernel/userspace result. This is the fixture's configuration-path mismatch, not evidence about the physical device's stub. Exact details are in the mismatch audit and corrected-run summary cited below.

## Minimum safe restored-target fixture test

Use a new isolated COW work directory. Treat all sources as read-only: target root QCOW, restored ESP FAT bytes, rescue media, and source firmware vars. Make a fresh disposable ESP wrapper from the exact restored `C1D2-E253` bytes, correct only the *wrapper copy* of the GRUB stub to load the known existing `($root)/grub/grub.cfg`, and use a fresh AAVMF vars copy with one-time BootNext pointing to that wrapper's unique GPT GUID. Attach the target root as a qcow2 COW overlay; do not attach the rescue disk after restore. Capture serial and bounded SSH health until the target userspace is demonstrably running. Record `uname -r`, root filesystem identity, ESP source/UUID and read-only mount state, active payload hashes versus recovery manifest, marker/staging state, package audit, and read-only FAT check after shutdown. This single fixture run validates the exact restored ESP through userspace without claiming physical loader equivalence.

Minimum scratch planning for this bounded follow-up: reserve **1 GiB** for the 512 MiB GPT-wrapped ESP copy, fresh 64 MiB variable store, root COW growth, logs, and checks; set a hard cap of **2 GiB** and stop before exceeding it. The current worker instruction's 500 MiB allocation cap is too small for a full 512 MiB ESP wrapper plus VM overhead, so this run was correctly not started in this wave. The documented broader FAT EIO guest matrix estimates **6–10 GiB peak for one VM** (fresh root overlay, FAT copies and vars), run sequentially; that remains separate from the minimum restore-userspace boot.
