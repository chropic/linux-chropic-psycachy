# Independent review: AMD64 activation patch

## Verdict

**Approved with one explicit assurance limitation; no code-level blocker found in the reviewed patch.** The first-install wording now accurately limits its claim: it confirms that no prior PsyCachy candidate payload is displaced, and expressly warns that other disk contents are not preserved. Replacement requires an actual, revalidated archive and manifest on a separate serial-identified disk before preparation. The state machine keeps Ubuntu as the saved default through acknowledgement and makes rollback available after acknowledgement and promotion.

The local health-attestation mechanism is a structured operator gate, not a cryptographically independent attestation. A root user can write the JSON, choose the reviewer string, timestamp, and true gate values; the helper checks binding and file safety but does not verify reviewer identity or a signature. Treat it as an auditable workflow record, not proof that an independent reviewer or physical GPU/recovery check actually occurred. If independent approval is a release requirement, require a signed attestation or out-of-band approval before promotion.

## Claim-by-claim review

- **Selector, first-install/replacement, pre-erase gate — approved.** `iso/select-disk.py` asks for an explicit mode before the final `ERASE` confirmation. First-install confirmation says no prior PsyCachy candidate payload is displaced and warns that other disk contents are not preserved. Replacement asks for the reviewed manifest hash and volume UUID, then verifies the backup before allowing erase confirmation. A root-owned, mode-0600 activation record is written only after the exact `ERASE` response and binds the decision to the selected serial. The selector re-discovers the disk before configuring autoinstall.
- **Backup independence and persistence — approved for the implemented checks.** `verify_displaced_backup` checks manifest/archive identity, exact volume UUIDs, direct physical-disk ancestry, distinct backup and target serials, archive hash, and displaced-package identities. `late-install.sh` confirms root and EFI resolve to the same selected disk, compares the current target serial to the pre-erase record, and copies the record into the target. `prepare_locked` re-verifies the same backup and compares every recorded identity field. These checks establish separation at verification time; retained media availability/persistence remains unexercised in the supplied evidence.
- **NVIDIA package and module verification — approved with scope understood.** Installer verifies the offline repository checksum manifest, requires exactly one matching open driver/DKMS pair, records package hashes/version/name, installs that pair, and checks installed DKMS state plus required module signature markers. The trial helper checks root-only identity metadata and installed package status/version/architecture; its runtime candidate-integrity check binds the metadata file and validates the required module signatures cryptographically against the pinned local module certificate, kernel trust/lockdown, and loaded required modules. The recorded NVIDIA deb hashes are not independently re-derived from installed dpkg state later; installed package files are verified by the package-manager state/version checks, while required kernel modules get signature checks.
- **Signing identity separation — approved.** Static reviewed package pin identities are kept distinct from per-install kernel/module certificate fingerprints and machine ID. Secure Boot candidate verification checks the pinned certificate hashes, enrollment, signed kernel and exact unsigned payload, plus module signatures. Secure Boot-disabled installations cannot promote.
- **Acknowledgement, attestation, promotion — approved with caveat above.** Acknowledgement requires candidate running, verified candidate integrity when Secure Boot is enabled, unchanged fallback, consumed one-time entry, clean package state, and required units. Promotion requires acknowledged state, candidate running, Secure Boot enabled, repeated integrity/fallback/package checks, no pending one-time entry, and bound local attestation. It uses `promotion_pending` around the GRUB default change, so interruption is represented and rollback accepts that state.
- **Rollback after acknowledgement/promotion — approved.** The interactive frontend offers rollback from acknowledged and promoted states. The helper accepts acknowledged, promotion-pending, and promoted states; verifies the fallback payload, handles candidate or fallback currently running, clears any one-time entry, restores the fallback as saved default, and reboots when needed. The boot-time unit remains available to finalize a fallback boot after rollback; acknowledgement disables only the timeout timer.
- **Installer packaging — approved by static path review.** `build.sh` adds the AMD64 pin/helper payloads, `late-install.sh` stages the trial helper, pin, secure-boot and activation scripts, and `install-target.sh` requires those files, installs the package pair/kernel, signs modules, verifies GRUB fallback/candidate entries, and places launchers/hooks. No built ISO was tested, so assembled-media packaging remains unverified at runtime.

## Remaining evidence boundary

The captured tests and static checks do not demonstrate a physical install, UEFI/Secure Boot enrollment, actual GPU module load/use, persistence of an external backup through reboot, human attestation, promotion, or rollback on target hardware. Those remain deployment acceptance evidence; they are not contradicted by this code review.
